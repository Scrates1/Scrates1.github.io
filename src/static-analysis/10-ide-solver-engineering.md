[第 08 篇](08-ide.md)已经得到跳转函数 `〈源事实,目标点,目标事实,函数〉`。实际程序可能产生大量这样的条目：同样的算法，怎样存、怎样查、何时释放，会影响它能否完成。

ECOOP 2024 论文 *Scaling Interprocedural Static Data-Flow Analysis to Large C/C++ Applications: An Experience Report* 从布局、批处理和回收三个方面优化 IDE 求解器。以下用一组自建条目解释这些做法，性能数据引用论文实验。[论文与出版信息](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ECOOP.2024.36)

## 1. 跳转函数的访问成本

假设节点 n 处有三条跳转函数：

| 源事实 d₁ | 目标事实 d₂ | 函数 |
| :--- | :--- | :--- |
| p | a | `t↦t+2` |
| p | b | `t↦5(t+2)` |
| q | b | 恒等 |

求解器更新其中一条时，需要定位旧函数、与新贡献合并，并判断是否重新入队。条目数相同，不同容器仍有不同的成本：重复的键、内层表对象、散列次数、扩容与额外索引都占时间或空间。可以把跳转函数表想成一个巨大的三级索引字典：算法本身不关心字典怎么实现，但每处理一条路径边都要查一次、写一次，字典的形状直接决定总耗时和内存。

## 2. 按访问方式选择映射布局

论文第 4.1 节比较的候选布局包括：

| 名称 | 结构 | 外层固定后还要查什么 |
| :--- | :--- | :--- |
| JF_old | `n → d₁ → d₂ → f` | 源事实、目标事实 |
| JF_ND | `(n,d₁) → (d₂ → f)` | 目标事实 |
| JF_N | `n → ((d₁,d₂) → f)` | 源目标事实对 |
| JF_NE | JF_N 加独立的出口摘要表 | 用额外存储改善摘要访问 |

JF_old 在新求解器中保留了原来的嵌套形状，但移除了旧实现维护的多索引，比较实验时需要计入这项差异。[论文第 4.1 节](https://drops.dagstuhl.de/storage/00lipics/lipics-vol313-ecoop2024/LIPIcs.ECOOP.2024.36/LIPIcs.ECOOP.2024.36.pdf)

在我们的三条记录中：

- JF_ND 为 `(n,p)` 和 `(n,q)` 各建立一个内层表。
- JF_N 只为 n 建立一个内层表，里面有 `(p,a)`、`(p,b)`、`(q,b)` 三个键。

若经常一次处理固定 n 下的很多事实，JF_N 能共用一次外层查找；若经常固定 n、p 查询，JF_ND 的内层表更直接，但可能需要更多小表。

因此，布局选择取决于哪些键经常一起使用，以及内层容器的数量和大小。

## 3. 批处理：复用外层查找

原本每次更新都从总表查起：

```text
for 每个目标事实 d2:
    old = table[n][d1,d2]
    new = old ⊔ candidate
    有变化则保存并调度
```

若这一批的 n 固定，可把查找移到循环外：

```text
row = table[n]
for 每个目标事实 d2:
    old = row[d1,d2]
    new = old ⊔ candidate
    有变化则保存并调度
```

本例用 Join 表示函数合并，论文按自己的顺序写 Meet；存储优化不改变合并语义。一次批处理包含 k 次更新时，外层定位由 k 次降为一次，内层更新和变化检测仍然都要做。

论文算法 1 将这样的局部视图传给 Propagate，在保留全部更新的同时复用查找结果。[论文算法 1 与表 2](https://drops.dagstuhl.de/storage/00lipics/lipics-vol313-ecoop2024/LIPIcs.ECOOP.2024.36/LIPIcs.ECOOP.2024.36.pdf)

## 4. 有了摘要，能把方法内部条目全删掉吗？

calc 的内部保存 `p→a`、`p→b`，出口保存 `p→ret`。只查询调用者返回值时，部分中间条目可以回收；不过，IDE 第二阶段还要利用函数计算值，释放之前需要确认后续求解不再使用它们。直觉上“说明书写好了，草稿就能扔”，难点在于判断草稿确实没人再看：可能还有调用者在等这份摘要，摘要应用后又可能产生新的向前任务。

论文第 4.2 节将生命周期与两类工作列表结合：

- PathWorkList：待处理的向前传播。
- RetWorklist：待应用到调用者的摘要。

回收某过程的中间条目，需要确认两个列表中都没有该过程或其传递被调用者的待办；还要保留后续需要的结果与值传播信息。关键保留项包括出口摘要、感兴趣查询点，以及用于过程入口值传播的调用点。

假设 p 调用 q，此时：

1. q 的摘要刚产生，仍在返回列表里等待应用给 p。
2. 若此时仅因 p 的向前列表为空，就删除 p 的相关信息，后续摘要应用可能又要求继续处理 p。
3. 等 q 的摘要应用完，并处理完由此产生的新任务，才能按保留规则回收 p 的中间条目。

论文的调度先推进向前传播，再处理返回应用，在适当阶段检查回收。返回应用可能再次产生向前任务，因此外层仍需要迭代。[论文算法 2、3 与第 4.2.2 节](https://drops.dagstuhl.de/storage/00lipics/lipics-vol313-ecoop2024/LIPIcs.ECOOP.2024.36/LIPIcs.ECOOP.2024.36.pdf)

若业务必须查询所有节点的值，内部节点也都需要保留，回收空间就会缩小，甚至完全消失。

## 5. 实验结果与比较基线

论文评估了 31 个 C/C++ 程序，使用类型状态分析（Typestate）、线性常量分析（LCA）和指令交互分析（IIA）。实验节点为 AMD EPYC 72F3，内存限制 250 GiB，超时限制四小时。下表来自表 3，列出平均比值及标准差：

| 分析 | 内存：旧/新 | 时间：旧/新 |
| :--- | :--- | :--- |
| IIA | `4.811 ± 1.192` | `7.227 ± 2.042` |
| LCA | `1.729 ± 0.365` | `4.683 ± 2.150` |
| Typestate | `0.968 ± 0.050` | `1.162 ± 0.143` |

**比较双方是原 IDESolver 与使用 JF_old 的 IDESolver++。** 7.227 倍反映了索引、批处理等实现的整体变化。换用 JF_N、启用 GC 的增量收益由另外的实验测量，见论文表 4、图 6。[论文第 6 节，尤其表 3](https://drops.dagstuhl.de/storage/00lipics/lipics-vol313-ecoop2024/LIPIcs.ECOOP.2024.36/LIPIcs.ECOOP.2024.36.pdf)

比值大于 1 表示改善，小于 1 表示该项变差。因此 Typestate 的内存比没有显示平均节省。不同分析的事实数量和稀疏程度不同，收益不能直接移植到 Java 污点分析。

还需将“完成的任务”“超时”“内存不足”一起看：从内存不足变为超时，不等于已经完成，也不必然意味着算法变慢。仅统计成功案例的平均耗时会遗漏这些差异。

## 6. 同一问题的其他路线

论文的实现基于 [PhASAR](https://phasar.org/)，在不改变算法语义的前提下压缩了条目的存储与访问，属于“让同样多的工作做得更省”。让 IFDS/IDE 扩展到大程序还有几条不同思路，它们改变的是要做多少工作：

| 路线 | 做法 | 减少的成本 | 代表 |
| :--- | :--- | :--- | :--- |
| 稀疏化 | 事实只在定义与使用它的语句之间传播，跳过与该事实无关的程序点 | 恒等边的传播次数与路径边数量 | [SVF](https://github.com/SVF-tools/SVF) 的稀疏值流图 |
| 按需求解 | 只从查询点出发，向前或向后探索到足以回答的范围 | 与查询无关的整程序传播 | [Boomerang](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ECOOP.2016.22) 的按需别名查询；[同步下推系统](https://www.bodden.de/pubs/sab19context.pdf)同时处理调用与字段两种括号 |
| 摘要复用与回收 | 跨方法复用摘要，方法内部条目用完即释放 | 内存峰值 | 本篇论文的 GC；FlowDroid 等工具的方法摘要 |
| 并行与增量 | 按方法或按查询并行求解；代码改动后只重算受影响部分 | 挂钟时间 | 多数工业求解器的工程实现，公开评测较少 |

这些路线可以叠加，但各有前提：稀疏化要求先建好定义使用关系，按需求解要求客户端能给出具体查询，回收依赖第 4 节讨论的调度不变式。评估自己的求解器时，先判断瓶颈在条目数量、条目访问还是无关传播，再选路线。

## 7. 怎样迁移到自己的求解器？

将这些做法用于自己的实现时，可以按以下顺序评估：

1. 记录跳转函数条目数、各索引规模、容器分配，以及最频繁的查询键组合。
2. 对固定节点的一批更新，测试复用内层表能节省多少查找，同时测量小表增多的代价。
3. 固定输入、模型、种子与预算，分别测量布局、批处理和回收的收益。
4. 比较优化前后各查询点的值与报告，确认结果一致。
5. 同时记录内存峰值、耗时、超时与 OOM，让未完成的任务也进入对照。

## 本篇要点

- 跳转函数表是求解器最频繁读写的结构；**布局**（JF_old/ND/N/NE）要按“哪些键经常一起查”选择。
- **批处理**把固定节点下的外层查找移到循环外，只减少定位次数，合并与变化检测仍逐条做。
- **回收**方法内部条目的前提是两个工作列表中都没有该方法及其被调者的待办，且保留出口摘要、查询点和入口值传播所需的调用点。
- 论文表 3 的倍数是“旧求解器 vs 新求解器（JF_old）”的整体差异，Typestate 的内存并未改善；数字不能直接移植到 Java 污点分析。
- 存储优化让同样的工作做得更省；稀疏化、按需求解、并行与增量则减少要做的工作，可叠加但各有前提。
- 迁移到自己的求解器：先量条目数与查询键组合，再分别测量每项优化，最后核对结果一致并把超时/OOM 计入对照。
