                                        09｜符号执行与 Clang：怎样排除不可行路径？

                                        远起大约 5 分钟静态分析符号执行Clang Static Analyzer路径敏感

                                        读前须知

                                        读过第 03 篇即可理解路径推演，调用相关内容用到第 06 篇。本篇观察路径条件怎样排除误报；第 6 节与 IFDS/IDE 的比较需先读第 07、08 篇。

                                        **符号执行（symbolic execution）**在状态中保留路径条件，用约束判断后续分支是否可行。

                                        # 1. 两个互斥的分支

                                        假设 flag 中途不变，input 是来源，sink 是敏感操作：

                                        String y = "safe";
if (flag)  y = input();
if (!flag) sink(y);

                                        合并式 may 分析可能记录 y 有污点，再把它送到 sink。但来源赋值要求 flag 为真，执行 sink 要求 flag 为假。要发现冲突，状态必须保留这两个条件。

                                        # 2. 符号值与路径条件

                                        用符号值（symbolic value）为未知量命名：β 代表 flag，σ 代表 input 的结果。沿途分支的要求累积为路径条件（path condition）；条件无法同时成立时，就是不可行路径（infeasible path）。

                                        沿 CFG 保存值与路径条件，可以得到以下推演；这张表是语义示例，并非 Clang 运行日志。

                                        到达位置路径条件y 的值与来源下一步
                                        第一次 if 之前true，无额外约束"safe"分成两条状态
                                        第一分支为真之后βσ，来自 input第二个 if 要求 ¬β 才进入
                                        第一分支为假之后¬β"safe"第二个 if 可进入
                                        污点状态尝试进入 sinkβ ∧ ¬βσ条件冲突，排除
                                        安全状态进入 sink¬β"safe"可行，但没有污点

                                        ¬ 读作“非”，∧ 读作“且”。这里的冲突只涉及同一个布尔符号，无需复杂算术求解。

                                        # 3. 路径探索的限制

                                        实际引擎的探索能力受三方面限制：

                                        • 内存对象、别名与库行为如何表达。
                                        • 约束管理器能表达和求解哪些条件；超出能力的条件只能保留为未知。
                                        • 循环探索、内联与节点数预算；具体限制取决于版本和分析器配置open in new window。

                                        逐路径展开 n 个独立的 if，最多产生 2ⁿ 条路径。未知条件保留两个分支，可能引入误报；预算耗尽而放弃剩余探索，则可能漏报。

                                        若 flag 在两次判断之间被重新赋值，两次测试可能不再对应同一符号，原来的矛盾推导就失效。

                                        # 4. Clang 的位置与状态表示

                                        Clang 的编译路线与分析路线已在第 02 篇第 5 节图 6 定位。Static Analyzer 在源码级表示上做路径敏感探索，图节点 ExplodedNode 包含 ProgramPoint 和 ProgramState。检查器开发手册open in new window

                                        对象作用与上例的对应
                                        ProgramPoint执行位置及处理阶段第二个 if 之前、调用 sink 之前
                                        Environment表达式到 SVal 的映射；SVal 是符号值、具体值或内存位置的统一表示某表达式当前求得的值
                                        Store内存区域到值的映射局部变量 y 所在区域保存的值
                                        GenericDataMap约束及检查器自定义数据对符号的限制、来源等额外状态

                                        后三项构成 ProgramState 的主要内容，ConstraintManager 则负责约束的推理与更新。定义可对照 ProgramState.hopen in new window，Store 的区域建模见 Region Store 文档open in new window。

                                        同一程序点可保留 β、¬β 路线上的不同状态，也可共享已有节点，组成 ExplodedGraph。

                                        # 6. 与 IFDS/IDE 的组织方式比较

                                        维度IFDS/IDEClang Static Analyzer
                                        节点与边携带的信息节点是程序点加单事实；IDE 在边上另有值变换节点是程序点加一份抽象状态
                                        跨函数组织匹配路径与过程摘要上下文中的调用探索、内联及模型
                                        条件关联需显式编码或另外处理状态中维护路径约束
                                        主要成本事实域、路径边、跳转函数和摘要状态分叉、约束及调用展开

                                        # 本篇要点

                                        • 符号值与路径条件保留分支关联，可排除 β∧¬β 这样的不可行路径。
                                        • 精度与覆盖受模型、约束能力及探索预算限制；赋值后需更新符号绑定。
                                        • Clang 以程序点和状态组成 ExplodedNode，检查器通过回调更新不可变状态，避免混淆路径。
                                        • IFDS/IDE 以事实关系和摘要组织传播；Clang 以抽象状态、调用探索与模型组织分析。
