## 一、程序分析的基础问题

### 1.1 程序分析要解决什么

本文关注静态分析：**不实际运行程序，通过代码推断它可能出现的行为。** 例如，用户输入是否会未经处理到达危险操作，某个变量在使用前是否已初始化。

实际程序有分支、循环和递归，分析器不能依靠枚举所有执行来得到答案。因此需要**抽象**：只保留当前问题需要的信息。例如，分析污点时关心“是否来自不可信输入”，通常不需要知道输入字符串的每个字符。

同一个变量也可以用不同精度描述：

| 信息           | 含义          | 精确度   |
| :------------- | :------------ | :------- |
| `x = 5`        | 确定是 5      | 最精确   |
| `x ∈ {0, 5}`   | 可能是 0 或 5 | 较精确   |
| `x 是任意整数` | 什么都不知道  | 最不精确 |

**精确度描述的是排除了多少不可能的行为。** 一个结果可能很保守，却仍然可靠：把真实行为全部包含在内，但额外包含一些不会发生的行为。这些额外可能性可能产生误报；若漏掉真实行为，则可能漏报。

因此，需要分别看两件事：**模型是否覆盖真实行为，求解器是否准确求出了这个模型的结果。** 后面说 IFDS 的“精确求解”，主要指第二件事，不等于告警没有误报。

### 1.2 两种主要范式

|              | 数据流分析               | 符号执行                 |
| :----------- | :----------------------- | :----------------------- |
| **核心操作** | 在格上迭代，合并信息     | 模拟执行，收集路径约束   |
| **状态**     | 格元素（抽象信息）       | 符号值、内存和路径约束  |
| **路径处理** | 合并，路径不敏感（通常） | 分叉，路径敏感           |
| **合并操作** | 合并各路径的信息，本文按精确度排序时使用 Join | 通常不合并（或有限合并） |
| **终止控制** | 有限高度上的单调迭代，或使用 widening 等方法 | 限制循环展开、递归和探索预算等 |
| **强项**     | 可扩展性，处理大规模程序 | 精确的路径推理           |

这是一种入门对比，两者可以结合。数据流分析也可以在抽象状态中携带路径信息；符号执行同样需要抽象和资源控制。

### 1.3 贯穿示例：一条污点怎样到达使用点

下面是简化的 Java 伪代码。假设 `input()` 返回不可信输入，`sink()` 是需要检查输入的敏感操作：

```java
String x = input();
String y = "safe";
if (flag) {
    y = x;
}
sink(y);
```

这里只跟踪局部变量，暂不涉及堆对象和别名。分析器把“x 可能有污点”简写成事实 `x`：

| 程序位置 | 可能有污点的变量集合 | 原因 |
| :--- | :--- | :--- |
| `x = input()` 之后 | `{x}` | 输入产生污点 |
| `y = "safe"` 之后 | `{x}` | 安全常量不带污点 |
| 执行 `y = x` 的分支末尾 | `{x,y}` | x 的污点传播给 y |
| 跳过赋值的分支末尾 | `{x}` | y 仍是安全常量 |
| `sink(y)` 之前 | `{x,y}` | 两条路径取并集，y 可能有污点 |

这个例子已经包含后面要解释的三个对象：**集合保存分析状态，流函数描述语句的影响，Join 合并分支结果。**

## 二、格理论（数学基础）

### 2.1 偏序关系（Partial Order）

**偏序关系**描述元素之间的顺序，但不要求任意两个元素都能比较。在分析中，我们通常用它比较信息精确度：`{x}` 和 `{x,y}` 可以比较，而 `{x}` 与 `{y}` 分别排除了不同的可能性，不能简单说谁更精确。

#### 严格定义

一个集合 \( S \) 上的二元关系 \( \sqsubseteq \) 如果满足以下三条性质，就叫**偏序关系**：

> **符号读法**：\( a \sqsubseteq b \)（`a ⊑ b`）读作“a 在偏序下小于或等于 b”。具体含义取决于关系的定义；若 `⊑` 是集合包含 `⊆`，就读作“a 是 b 的子集”。

1. **自反性**：对任意 \( a \in S \)，有 \( a \sqsubseteq a \)。读作“a 在偏序下小于或等于它自己”；若采用集合包含关系，就是“每个集合都是自身的子集”。
2. **反对称性**：若 \( a \sqsubseteq b \) 且 \( b \sqsubseteq a \)，则 \( a = b \)。
3. **传递性**：若 \( a \sqsubseteq b \) 且 \( b \sqsubseteq c \)，则 \( a \sqsubseteq c \)。

满足这三条，\( (S, \sqsubseteq) \) 就是一个**偏序集（Poset）**。

#### 偏序与全序的区别

| 概念         | 含义                                  | 例子                     |
| :----------- | :------------------------------------ | :----------------------- |
| **偏序关系** | 满足自反性、反对称性和传递性；不要求任意两元素可比较 | 幂集 \( \mathcal P(\{1,2\}) \) 上的包含关系 \( \subseteq \)；其中 `{1}` 与 `{2}` 不可比较 |
| **全序关系** | 满足偏序的要求，且任意两元素都可比较 | 实数上的 \( \le \) |

**符号说明**：`𝒫` 表示幂集（所有子集组成的集合），`∅` 是空集，`⊆` 读作“是……的子集”（允许相等）。例如：

```text
𝒫({1,2}) = { ∅, {1}, {2}, {1,2} }
```

“幂集上的包含关系”就是用 `⊆` 比较这四个集合：`{1} ⊆ {1,2}`，但 `{1}` 与 `{2}` 互不包含，因而不可比较。**偏序允许存在不可比较的元素，但不要求一定存在。**

**全序是偏序的特殊情况。** 同样是集合包含关系，如果只考虑集合族 `{∅, {1}, {1,2}}`，就有 `∅ ⊆ {1} ⊆ {1,2}`，任意两个元素都可比较，因此它在这个集合族上构成全序。判断是否为全序，需要同时看参与比较的元素和所定义的关系。

### 2.2 格：Join 和 Meet 的定义

**格（Lattice）**是任意两个元素都有最小上界和最大下界的偏序集：

| 操作 | 符号 | 定义 |
| :--- | :--- | :--- |
| **Join** | `⊔` | 最小上界：在两者上方的所有元素中，位置最低的那个 |
| **Meet** | `⊓` | 最大下界：在两者下方的所有元素中，位置最高的那个 |

这里的“上、下”和“最小、最大”都按偏序 `⊑` 判断，不是按集合的元素数量判断。以 Join 为例：

1. `A ⊑ A⊔B` 且 `B ⊑ A⊔B`：它是两者的上界。
2. 若 U 也是两者的上界，则 `A⊔B ⊑ U`：它是所有上界中最小的。

定义先记到这里。下面把集合的含义、图上的方向和实际合并放在同一个例子里看。

### 2.3 用污点与初始化理解幂集格和合并

事实域 `D` 包含分析要跟踪的事实；一个分析状态是 `D` 的子集，所有这样的状态构成幂集 `2^D`，也就是 2.1 节的 `𝒫(D)`。给它配上合适的偏序，就得到幂集格。

#### 先固定本文的画法

**本文统一约定：越往上越不精确。** `A ⊑ B` 表示 A 至少和 B 一样精确，因此把 A 画在 B 下方。

这里“更精确”指**对程序状态知道得更具体**，不是“结论更正确”。合并两条路径后不知道实际走了哪条，只能保留对两条路径都适用的信息；结果相对每条路径可能损失精度，也可能不变。按本文约定，合并向上寻找最接近两者的共同上界，即 Join。

#### May：哪些变量可能有污点？

集合中的 x 表示“x 可能有污点”。假设路径 A 得到 `{x}`，路径 B 得到 `{y}`。两种可能都要保留，因此合并取并集：

```text
              {x,y}          合并结果：x、y 都可能有污点
              ↗   ↖          向上合并：Join = 并集
           {x}     {y}
          路径 A   路径 B
```

`{x} ∪ {y} = {x,y}`。相比只记录 `{x}`，合并结果不能再排除 y 有污点的可能性：**候选更多，信息更不精确，所以大集合放在上面。** 此时 `⊑` 对应 `⊆`。

`{x,y}` 不要求 x、y 在同一次执行中同时有污点。`∅` 表示没有变量被标记为可能有污点，`D` 表示所有被跟踪的变量都可能有污点。

#### Must：哪些变量保证已初始化？

这次集合中的 x 表示“x 保证已初始化”。假设路径 A 得到 `{x,y}`，路径 B 得到 `{x,z}`。只有 x 是双方共同保证的，因此合并取交集：

```text
                {x}          合并结果：只能保证 x 已初始化
               ↗   ↖         向上合并：Join = 交集
           {x,y}   {x,z}
           路径 A   路径 B
```

`{x,y} ∩ {x,z} = {x}`。相比路径 A，合并后失去了“y 已初始化”的保证。**`{x}` 不表示 y 未初始化，而是对 y 没有保证**：y 已初始化和未初始化两种情况都允许。因此，保证减少，信息也更不精确；小集合放在上面，`⊑` 对应 `⊇`。

为什么 `{x}` 是最小上界？在反向包含排序下，A、B 的上界必须是双方的共同子集。候选有 `{x}` 和 `∅`，而 `{x} ⊑ ∅`，所以 `{x}` 是位置更低、信息更精确的那个。

#### 两个场景，合并方向相同

| 本文约定：向上更不精确 | May：可能有污点 | Must：保证已初始化 |
| :--- | :--- | :--- |
| 集合增大意味着 | 可能性更多，更不精确 | 保证更多，更精确 |
| 偏序 `⊑` | 包含 `⊆` | 反向包含 `⊇` |
| 路径汇合 | 取并集，向上，是 Join | 取交集，向上，也是 Join |
| 顶元素 `⊤` / 底元素 `⊥` | `D` / `∅` | `∅` / `D` |

**合并向上，是因为结果不比输入更精确；集合变大还是变小，则取决于它记录“可能性”还是“保证”。** 图中的连线表达信息顺序，不是程序执行的控制流。

#### 读其他资料时：如果作者把图翻过来

抽象解释中常采用本文这种“向上更不精确”的约定；部分经典数据流资料采用相反方向。若把上面两张图都上下翻转：

| 作者的排序约定 | May 合并 | Must 合并 |
| :--- | :--- | :--- |
| 向上更不精确（本文） | 向上取并集，叫 Join | 向上取交集，叫 Join |
| 向上更精确 | 向下取并集，叫 Meet | 向下取交集，叫 Meet |

例如，第二种画法中 `{x,y}` 会位于污点结果 `{x}`、`{y}` 的下方，成为它们的最大下界。**结果仍是并集 `{x,y}`，只是位置和名称变了。** 初始化保证同理，仍取交集 `{x}`。

整体反转偏序称为**序对偶（order duality）**，写作 `A ⊑ᵒᵖ B ⇔ B ⊑ A`；原格的 Join/Meet、顶/底随之交换。它不改变哪个结果更具体，只改变怎样给这些结果排序。

资料通常通过偏序公式、顶底元素或格图交代约定，不一定直接说“向上更精确”。例如常量分析写 `常量3 ⊑ 未知`，就是向上更不精确；写成反向关系则相反。可对照 [Cousot 的抽象解释介绍](https://www.di.ens.fr/~cousot/COUSOTpapers/publications.www/Cousot-SSGRR-00.pdf)与 [Cornell 的数据流课程](https://courses.cs.cornell.edu/cs4120/2022sp/notes/)。

**后文固定回到 may 污点分析：按 `⊆` 排序，取并集向上合并，称为 Join。** 无需在两种约定间反复切换。

### 2.4 高度有限（Finite Height）

**有限高度**为单调的不动点迭代提供了终止保证。

循环会把分析结果送回前面的程序点，因此一次遍历通常不够。分析器反复传播新信息，直到每个位置的结果都不再变化，这就是**不动点**。

#### 什么是“高度”？

在偏序集里，**链（Chain）** 是指一串两两可比较的元素：

\[
a_0 \sqsubset a_1 \sqsubset a_2 \sqsubset \cdots
\]

**高度（Height）** 就是**最长链的长度**。

**高度有限**的意思是：**严格链的长度有一个统一的有限上界**，因此不可能一直严格上升。

#### 为什么高度有限如此重要？

以 may 事实集合为例，不动点迭代通常这样进行：

1. 设置入口种子，其余程序点从空集开始。
2. 用流函数计算后继事实，与后继已有结果取并集；有变化就继续传播。
3. 没有新事实需要传播时停止。

**在有限程序图上，单调流函数配合适当初始化和单向更新，有限高度就能保证迭代终止。** 对无限高度的域，可以用 widening（加宽）等方法促使迭代收敛。

这里的**单调**是指 `A ⊑ B` 时有 `f(A) ⊑ f(B)`。在本文的集合包含排序下，它表示输入增加可能事实时，输出不会反而减少可能事实。它不要求 `S ⊆ f(S)`：例如，安全赋值会删除目标变量的污点，这仍然可以是单调函数。

#### 在 IFDS 里高度有限的意义

IFDS 的格是幂集格 \( 2^D \)：

- **\( D \) 有限** → 幂集格有限 → 高度有限。
- 按严格上升的步数计，高度为 \( |D| \)。
- 单个程序点的事实集合最多成功新增 \( |D| \) 个事实，但这不等于 IFDS 求解器的总迭代次数，因为它还要维护路径边和过程摘要。
- **有限事实域和分配律使 IFDS 可以通过专门的 tabulation 算法在多项式时间内求解。**

### 2.5 分配律（Distributivity）

分配律说明：**可以先合并再传播，也可以先分别传播再合并，结果相同。** 它让集合上的计算能被拆成单事实之间的传播，是 IFDS 转换成图问题的关键。

#### 定义

\[
f(A \cup B) = f(A) \cup f(B)
\]

`f` 是**流函数（flow function）**：输入执行语句前的事实集合，输出执行后的事实集合。`∪` 读作“并集”。公式要求对任意输入集合 A、B 都成立。

#### 满足分配律的例子

考虑贯穿示例中的 `y = x`。为了正确处理覆盖赋值，先删除 y 的旧污点，再根据 x 是否有污点决定是否加入 y：

```text
f(S) = (S − {y}) ∪ ({y} 若 x∈S，否则 ∅)
```

设 x、y、z 互不相同，z 用来表示另一个不受赋值影响的变量。观察几组输入：

- `f({x}) = {x, y}`
- `f({z}) = {z}`
- `f({x, z}) = {x, z, y}`
- `f({x}) ∪ f({z}) = {x, y} ∪ {z} = {x, y, z}`

这组输入说明了分配效果；一般地，删除固定事实与由单个 x 生成 y 都对并集分配，所以整个函数满足分配律。注意 `f({y})=∅`：赋值会覆盖 y，不能无条件保留它原来的污点。

#### 违反分配律的例子

设有三个抽象事实 p、q、r，规则要求**同时存在 p 和 q 才新增 r**：

```text
g(S) = S ∪ ({r} 若 p∈S 且 q∈S，否则 ∅)
```

验证：

- `g({p}) = {p}`，`g({q}) = {q}`。
- 分别处理再合并：`g({p}) ∪ g({q}) = {p,q}`。
- 先合并再处理：`g({p,q}) = {p,q,r}`。

两种顺序得到不同结果，因此 g 不满足分配律。单独传播 p 或 q，都无法表达这个联合触发条件。

#### 核心洞察

**关键是：集合的整体效果能否由单事实效果加上无条件生成的事实组合得到。** 对有限集合，可写成：

\[
f(S) = f(\varnothing) \cup \bigcup_{d \in S} f(\{d\})
\]

`⋃` 表示把各个结果取并集。这个公式把流函数分为两部分：`f(∅)` 是**无条件生成**，其余是**各输入事实独立产生的结果**。

单调性支持有序迭代，分配性进一步支持这种拆分。满足分配律的函数必然单调，但单调函数未必分配；上面的 g 就是一个例子。

## 三、IFDS 框架

### 3.1 基本设定

**IFDS（Interprocedural Finite Distributive Subset）** 是求解**过程间、流敏感、上下文敏感**数据流分析的一个经典算法。

**核心思想**：把数据流分析问题转换成图上的可达性问题。

**三个关键要求**：

1. **有限（Finite）**：数据流事实域 `D` 有限。
2. **分配（Distributive）**：流函数满足分配律 `f(A ∪ B) = f(A) ∪ f(B)`。
3. **子集（Subset）**：每个程序点的信息是 `D` 的一个子集。

这里采用并集合并的形式。IFDS 也能处理对交集分配的问题，可通过对偶转换来求解。

第二章的概念在这里各有用途：**有限事实域限制求解规模，分配律允许拆成单事实传播，过程摘要支持跨调用复用。**

### 3.2 核心概念

#### 程序点（Program Point）

**程序点就是代码里的一个位置**，如语句、基本块入口或调用点。在 IFDS/IDE 中，它通常对应过程间控制流图（ICFG）的节点 `n`。本文示例约定节点上的事实表示**执行该语句之前**的信息。

#### 事实（Fact）

**事实是分析选择跟踪的一项性质。** 在贯穿示例中，`x` 代表“x 可能有污点”，`y` 代表“y 可能有污点”，普通事实域是 `D={x,y}`。其他分析可以跟踪“文件句柄处于打开状态”等性质，但域必须有限。

#### 程序点事实（Program Point Fact）

把位置和事实放在一起，得到二元组：

\[
(n, d)
\]

其中 `n` 是位置，`d` 是事实。例如 `(n_sink,y)` 表示：执行 `sink(y)` 前，y 可能有污点。它包含**一个位置和一个事实**，不是该位置的完整状态。

#### Λ（重言式事实）

**Λ（读作 Lambda）是辅助事实，也常称为 zero fact。它不属于普通事实域 `D`，也不等同于空集 `∅`。**

它解决一个具体问题：执行 `x = input()` 时，即使输入集合为空，也要生成污点 x。图上用 `Λ → x` 表示这种无条件生成，用 `Λ → Λ` 把辅助事实继续向后传递。Λ 本身不代表某个变量有污点。

本文采用单入口模型，以 `(s_main, Λ)` 为分析起点；实际求解器也可以支持多个种子。

### 3.3 控制流图（CFG）

**控制流图**是程序的一种图形化表示，描述**程序执行时可能走的路径**。

#### 基本构成

- **节点（Node）**：程序中的一个基本块或一条指令。
- **边（Edge）**：从一个节点到另一个节点的控制流转移。

#### 一个简单例子

```text
n₁: x = input();
n₂: y = "safe";
n₃: if (flag)
n₄:     y = x;
n₅: sink(y);
```

对应的 CFG：

```
n₁ → n₂ → n₃ ──true──→ n₄ → n₅
             └──false────────→ n₅
```

#### 过程间控制流图（ICFG）

当程序有函数调用时，CFG 会扩展成**过程间控制流图（ICFG）**：

- 调用点有一条边进入被调用函数的入口。
- 被调用函数的出口有一条边回到调用点的下一条指令。
- IFDS 的图模型还包含 call-to-return 边，用来传递不需要经过被调用函数的事实，例如调用者中不受调用影响的局部变量事实。

### 3.4 爆炸超图（Exploded Supergraph, ESG）

IFDS 在 ICFG 的基础上构造**爆炸超图**：把“执行到哪里”和“传播哪个事实”同时放进节点。

#### 核心思想

**ICFG 的每个节点 `n`，在爆炸超图里被“炸开”成多个节点 `(n, d)`，每个事实 `d ∈ D ∪ {Λ}` 对应一个。**

- ICFG 节点：`n`（程序点）
- 爆炸超图节点：`(n, d)`（程序点事实）

#### 边的构造

假设在程序点 `n` 处，事实 `d` 成立，执行 `n` 后，流函数把 `d` 映射到事实 `d'`，那么在爆炸超图里就有一条边：

\[
(n, d) \to (n', d')
\]

在贯穿示例中，可以沿下面的事实链到达敏感操作：

```text
(n₁,Λ) ──输入生成──→ (n₂,x) ──保留 x──→ (n₃,x)
                                              │ true 分支
                                              ↓
                                           (n₄,x) ──赋值传播──→ (n₅,y)
```

这只是 ESG 的一条路径；完整图还包括 Λ 的传播、x 的保留以及另一条分支。**一个事实可以产生多个后继事实**，例如 `y=x` 既保留 x，又生成 y。

#### 为什么 `(n, d)` 可达 = 事实 `d` 在 `n` 处可能成立？

**这里的可达**：存在一条从 `(s_main, Λ)` 到 `(n, d)`、且**调用与返回正确匹配**的路径，称为 realizable path。

例如，调用点 A、B 都调用 `foo()`，从 A 进入的执行必须返回 A 对应的位置，不能沿 B 的返回边出去。普通图遍历不会自动排除这种交叉返回。

只要存在一条这样的路径，分析就保留事实 d，这对应 2.3 节的 may 语义。调用返回匹配还不保证分支条件可满足，这个区别在 3.7 节展开。

### 3.5 怎样高效求可达：Tabulation 与过程摘要

**Tabulation 可以理解为把已求出的传播关系记成表，供后续复用。** 求解器通过工作列表处理尚未完成的传播，并维护过程入口事实到过程内部或出口事实的关系。

例如，假设一个函数只把参数原样返回，它的摘要可以记录“参数的污点传到返回值”。以后从其他调用点进入时，可以把这个摘要应用到当前实参和返回位置，无需重复展开整个函数；调用返回仍按当前调用点匹配。递归情况下，摘要也通过迭代逐步稳定。

一般 IFDS tabulation 算法的时间界是 `O(|E| × |D|³)`：`E` 是过程间 supergraph 的边集，`D` 是普通事实域。当 `|E|=O(|N|)` 时，也常写成 `O(|N| × |D|³)`。

这个保证是**相对于图和事实域的规模**而言的。若为了提升精度而在事实里加入访问路径、对象或条件组合，`D` 本身就可能很大；多项式并不等于实际运行一定快。第五章讨论的正是这一点。

### 3.6 表示关系：把流函数变成边

第二章说明了分配函数能拆成单事实传播。**表示关系（Representation Relation）`R_f` 就是这种拆分的具体结果**：有序对 `(x,y)` 表示输入事实 x 可以产生输出事实 y。

注意，`(x,y)` 描述一次转移的事实关系；把它放到程序边 `n→n'` 上，才得到 ESG 边 `(n,x)→(n',y)`。

#### 标准构造

给定对并集分配的流函数 `f`，其中 x、y 取自普通事实域 `D`，构造三类边：

\[
R_f = \{(\Lambda, \Lambda)\} \cup \{(\Lambda, y) \mid y \in f(\varnothing)\} \cup \{(x, y) \mid y \in f(\{x\}), y \notin f(\varnothing)\}
\]

**含义**：

| 类型     | 含义                                      |
| :------- | :---------------------------------------- |
| `(Λ, Λ)` | 将辅助事实传递到下一程序点               |
| `(Λ, y)` | 从空集出发，流函数凭空产生的事实（gen）   |
| `(x, y)` | 单个事实 `x` 进去，产生了 `y`（transfer） |

公式里的 `|` 读作“满足”，`∈` 读作“属于”，`∉` 读作“不属于”。第三部分排除 `f(∅)` 中的结果，因为无条件生成已由 `Λ→y` 表示。

#### 用标准写法检验分配律

**例 1：`y = x` 的污点传播**，沿用 2.5 节的覆盖赋值函数。

- `f(∅) = ∅`，无凭空产生。
- `f({x}) = {x, y}`，有边 `(x, x)` 和 `(x, y)`。
- `f({z}) = {z}`，有边 `(z, z)`，表示保留 z。
- `f({y}) = ∅`，没有 `(y,y)`，因为旧的 y 被覆盖。

**结果**：`R_f = {(Λ,Λ)} ∪ {(d,d) | d∈D 且 d≠y} ∪ {(x,y)}`。除旧 y 外的事实被保留，x 还会产生新 y。这里假设 x、y 是不同变量，z 是其他变量。

**例 2：同时有 p、q 才新增 r。** 按 2.5 节的 g 计算，空集和单元素输入只能得到恒等边，无法表达 p、q 联合生成 r。这说明：非分配函数即使机械地套用上面的构造，也不能完整恢复原函数。

### 3.7 三种“敏感性”，分别保留什么信息

| 概念 | 关心的问题 | 示例 |
| :--- | :--- | :--- |
| **流敏感** | 是否区分语句执行顺序？ | `x=input(); x="safe";` 后，x 的旧污点应被覆盖 |
| **上下文敏感** | 是否区分不同调用上下文？ | 从调用点 A 进入函数，不能把返回传播到 B |
| **路径敏感** | 是否保留分支条件及其关联？ | 同一路径上的 `b` 与 `!b` 不能同时成立 |

IFDS 的调用返回匹配解决上下文问题，不会自动解决分支条件的可满足性问题。

#### IFDS 不自动判断路径可行性

IFDS 求解的是调用返回匹配路径上的数据流结果，常称为 **MRP（Meet over all Realizable Paths）**。**MOP（Meet over all Paths）** 则指所有路径上的结果，不能把它理解成“所有运行时可行路径”。这里的 Meet 沿用数据流文献的命名，具体合并运算仍取决于偏序约定。

#### 一个上下文匹配、但分支条件不可行的例子

```java
boolean b = flag;           // 后续不再修改 b
String y = "safe";
if (b)  y = input();
if (!b) sink(y);
```

忽略条件关联时，may 分析会在第一个分支后保留 y 的污点，并把它传播到 `sink(y)`。但实际执行中，污点赋值要求 `b`，敏感调用要求 `!b`，两者无法同时发生。要排除这条报告，需要额外的路径信息。

#### 怎样加入路径信息？

有两种思路：先用 IFDS 得到候选结果，再用符号执行或约束求解过滤；或者把“污点 + 有限条件状态”编码成一个事实，直接在传播中保留条件。

后一种方式仍需满足有限域和分配律，代价是事实域膨胀。若在原域上直接要求多个独立事实联合触发传播，则可能出现 2.5 节的非分配问题。

## 四、IDE 框架：从事实传播到值计算

### 4.1 与 IFDS 的关系

**IDE（Interprocedural Distributive Environments）** 是 IFDS 的**泛化**。

IFDS 回答“事实能否传播到这里”，IDE 还通过边函数计算传播后的值，并合并各条匹配路径的结果。为此，它将**有限的事实域**与**值域**分开。

通过两元素值格和适当的边函数编码，IFDS 可以作为 IDE 的特例。IDE 的优势是还能表达线性常量传播等值计算问题。

### 4.2 用常量传播理解环境与边函数

```java
int a = 1;
a = a + 2;
int b = a * 5;
```

这个例子选择 `D={a,b}`，把“每个变量对应什么抽象值”保存为环境 `D→L`。`L` 可以包含各个整数常量，以及表示不可达、未知等情况的特殊值；本文继续使用“越往上越不精确”的约定。

| 语句 | 事实之间的依赖 | 边函数及结果 |
| :--- | :--- | :--- |
| `a=1` | `Λ→a` | 无条件产生常量 1 |
| `a=a+2` | `a→a` | 输入值加 2，得到 3 |
| `b=a*5` | `a→b` | 输入值乘 5，得到 15 |

**流函数决定传播到哪个事实，边函数决定传播时怎样变换值。** 例如，`a→b` 表示依赖关系，`λv.5v` 表示“输入 v，输出 5v”；这里 `λ` 读作 lambda，是匿名函数记号，与辅助事实 `Λ` 是两回事。

同一路径上的边函数按执行顺序**组合**，多条路径到达同一事实时则**合并**。例如，若一个分支算出 `a=3`，另一个分支算出 `a=5`，简单常量域通常合并为“未知常量”，因为它无法用单个常量表示这两个结果。

IDE 要求相应的分配性和收敛条件，边函数还必须能有效求值、组合、合并和比较。表中的算术只展示常量输入；完整实现还要定义不可达、未知等特殊值的行为。

### 4.3 两阶段算法

IDE 的经典求解流程可以分为“先算传播关系，再代入入口值”两个阶段：

#### 阶段 I：计算跳转函数和过程摘要

从种子开始按需展开 ESG，通过 `Propagate` 等过程组合、合并边函数，直到跳转函数和过程摘要稳定。这一阶段保存的是**输入值到输出值的变换关系**，便于在不同调用上下文中复用。

#### 阶段 II：值计算

- **值传播**：从种子的初始值出发，利用跳转函数和调用关系计算各过程入口处的值。
- **值计算**：所有剩余跳转函数的边函数用先前聚合的值进行求值。

### 4.4 Jump Function（跳转函数）

**跳转函数把过程入口到某个节点之间的一段传播效果汇总起来。** 到过程出口的汇总则构成过程摘要的一部分。常用四元组表示：

\[
\langle d_1, n, d_2, f \rangle
\]

其中：

- `d₁`：所属过程入口 `s_p` 处的源事实
- `n ∈ N`：目标指令
- `d₂ ∈ D`：目标指令处的数据流事实
- `f ∈ J`：描述相应值计算的函数

源程序点 `s_p` 由目标节点 `n` 所属的过程隐含确定，因此没有单独写进四元组；实现中事实也可以是辅助事实 `Λ`。

例如，假设过程入口处参数 a 的值为 v，过程执行 `a=a+2; b=a*5;`。入口 a 到赋值后 b 的跳转函数就是：

```text
加 2，再乘 5：j(v) = 5 × (v + 2)
四元组：⟨a, n_after, b, j⟩
若入口 a=1，则 b=j(1)=15。
```

这一表示同时解释了复用与成本：摘要不必为每个具体输入重算，但求解器需要存储大量“源事实—目标节点—目标事实—函数”的条目。

## 五、IDE 的优化（论文核心内容）

> 本节内容基于论文《Scaling Interprocedural Static Data-Flow Analysis to Large C/C++ Applications: An Experience Report》（ECOOP 2024）。

前四章解释语义和算法，本章讨论工程成本。可以把两类优化分别理解为：**同样的跳转函数怎样存得更省、访问得更快；哪些中间跳转函数可以更早释放。**

### 5.1 问题背景

**论文考察的 IDE 实现（如当时的 PhASAR）在分析大型程序时遇到严重可扩展性问题**：

- 产生超过 1 亿条数据流边的分析无法在普通消费级硬件上完成。
- 分析 LLVM IR 中指令数少于 100,000 条的程序时，就很容易产生巨大的数据流数量。
- 许多有趣的数据流分析无法在中等规模到大型目标程序上求解。

### 5.2 优化一：跳转函数表数据结构

#### 现有表示

| 框架           | 表示                                  | 特点                 |
| :------------- | :------------------------------------ | :------------------- |
| PhASAR / Heros | 嵌套映射 `N → (D → (D → J))` + 多索引 | 可减少键重复，但增加查找层次和容器开销 |
| FlowDroid      | 扁平 `(N × D × D) → D`                | 查找快，但内存冗余   |

这里 `N` 是程序点集合，`D` 是事实域，`J` 是边函数集合。`N→(D→(D→J))` 可以读成“先按程序点找，再按源事实找，最后按目标事实找到函数”。FlowDroid 这一表示针对 IFDS，末尾再次存储目标事实是为了路径追踪，并不表示 IDE 的边函数也是一个事实。

#### 提出的折中方案

**两级嵌套映射**，减少嵌套深度。候选布局例如：

1. `(n,d₁) ↦ (d₂ ↦ f)` — `JF_ND`
2. `(n,d₂) ↦ (d₁ ↦ f)`
3. `(d₁,d₂) ↦ (n ↦ f)`
4. `n ↦ ((d₁,d₂) ↦ f)` — `JF_N`

这些是可选布局，不是需要同时维护的多份索引。论文最终评估了 `JF_ND`、`JF_N` 及其扩展 `JF_NE`。

**批处理优化**：在 Propagate 中，将循环不变部分作为外部映射的键，循环变体部分作为内部映射的键。

例如连续处理同一程序点 n 的大量事实时，先取出 n 对应的内层表，再在里面批量更新，避免每次都从最外层重新查找。布局是否有效，要看实际访问模式和容器开销。

#### 实现细节

- **开放寻址哈希**：缓存效率高，动态内存分配少。
- **32 位整数索引**：将节点和事实映射到连续整数范围。
- **SmallDenseMap**：内层映射使用小尺寸优化。
- **预分配**：外部哈希映射预分配合理大小。

### 5.3 优化二：跳转函数垃圾回收

不少内部跳转函数只在构造过程摘要时有用。摘要稳定后，如果后续传播和值计算都不再需要它们，就可以释放；最终结果需要查询的节点仍须保留。**回收的是不再需要的中间表示，不是任意丢掉分析结果。**

#### Arzt 的 GC（原始）

- 限于 IFDS 分析（不处理边函数）。
- 利用多线程，要求线程安全。

#### 扩展到通用 IDE

- **单线程 GC**：在 IDE 算法内显式调用。
- **两个工作列表**：
  - `Path WorkList`：自顶向下传播。
  - `Ret WorkList`：自底向上摘要应用。
- **GC 条件**：两个工作列表都不含 `p` 及其传递被调用者的节点。
- **感兴趣节点（Interesting Nodes）**：保留这些节点处的跳转函数。
- **调用点保留**：值传播需要所有调用点处的跳转函数。

调度可以改变处理顺序，但不能遗漏传播。上述回收条件必须同时检查两个工作列表，不能仅凭“当前没看到这个节点”就释放相关条目。

### 5.4 实验结果

#### 评估设置

- **31 个真实 C/C++ 程序**
- **三种分析**：TSA（类型状态分析）、LCA（线性常量分析）、IIA（指令交互分析）
- **计算集群**：AMD EPYC 72F3 8-Core，250GiB RAM

#### 主要结果

下表来自论文表 3：比较使用 `JFold` 布局的 IDESolver++ 与原 IDESolver，是基线实现的比较；数据布局和 GC 的额外收益在论文后续实验中单独评估。

| 分析      | 内存比（旧/新） | 耗时比（旧/新） |
| :-------- | :------- | :----------- |
| IIA       | 4.811×   | 7.227×       |
| LCA       | 1.729×   | 4.683×       |
| Typestate | 0.968×   | 1.162×       |

倍率大于 1 表示改善。Typestate 的平均内存比为 `0.968×`，低于 1，表示内存没有改善；将该汇总倍率取倒数约为 `1.033`，但这不等同于逐项内存增幅的算术平均。论文摘要将整体收益概括为平均最高约 **7 倍**，具体收益取决于分析类型和配置。

**关键结论**：

- 所有用 IDESolver 完成的实验，IDESolver++ 也能完成。
- 7 个原本占用超过 32GiB、最高达 143GiB RAM 的实验，现在可以在 32GiB 消费级硬件上运行。
- 3 个原本超时的实验，现在可以在时间限制内完成。

工程上值得带走的结论是：**算法复杂度相同，实现的内存布局、索引数量和中间结果生命周期，仍可能决定一个任务能否完成。**

## 六、Clang 静态分析器（对比范式）

### 6.1 核心原理：符号执行

Clang 静态分析器以**路径敏感的符号执行**为核心，沿路径维护抽象程序状态。

**它更像一个“源代码模拟器”**：

- 沿着控制流图追踪可能的执行路径。
- 用**符号（Symbol）** 代表未知的值。
- 遇到分支就**分叉**，收集路径约束。

用 3.7 节的例子理解：若某条路径已经记录 `b=true`，走到 `if (!b)` 时，约束推理可以发现该分支不可行，从而不再沿这条分支进入 sink。具体能排除多少不可行路径，取决于约束模型和探索预算。

### 6.2 ExplodedGraph

符号执行的状态和程序位置被组合成一个节点，构成 **ExplodedGraph**。

- **节点**：`(ProgramState, ProgramPoint)`
- **边**：状态转换

它与 IFDS 的 ESG 名字相近，但节点粒度不同：**IFDS 节点携带一个事实，Clang 节点携带一份抽象程序状态**，其中可以同时记录多个变量、内存信息及约束。

**ProgramState 内部包含**：

1. **Environment**：源代码表达式到符号值（SVal）的映射。
2. **Store**：内存区域到符号值的映射。
3. **GenericDataMap**：保存约束相关数据及检查器自定义状态。

**ConstraintManager** 负责约束的推理和更新，它是管理接口，不是上述第三个状态字段。

### 6.3 过程间分析

- **上下文敏感内联（Context-Sensitive Inlining）**：遇到函数调用时，在调用点的上下文中继续分析被调用函数。
- **无法展开的调用**：依赖函数模型，或对可能受影响的状态进行保守更新；实际精度取决于模型覆盖情况。

### 6.4 Checkers

分析引擎负责路径探索和状态转换，**检查器（Checkers）** 在此基础上实现具体规则，也可以参与状态更新。

检查器通过 `Checker<...>` 注册感兴趣的事件，例如：

- `check::PreCall` → `checkPreCall()`：调用前。
- `check::PostCall` → `checkPostCall()`：调用后。
- `check::PostStmt<DeclStmt>` → `checkPostStmt()`：声明语句处理后。

### 6.5 与 IFDS/IDE 的对比

| 特性           | Clang Static Analyzer   | IFDS / IDE             |
| :------------- | :---------------------- | :--------------------- |
| **核心方法**   | 符号执行 + 路径敏感模拟 | 数据流分析 + 图可达性  |
| **数学结构**   | 抽象程序状态（符号值、内存、约束） | IFDS：事实幂集；IDE：环境和值格 |
| **合并操作**   | 通常分开探索不同状态，可共享相同状态节点 | 按分析定义合并事实或值 |
| **状态表示**   | ExplodedGraph 节点      | 爆炸超图节点           |
| **上下文敏感** | 内联函数调用            | 过程摘要（Summary）    |
| **强项**       | 精确的路径推理          | 处理大规模过程间分析   |
| **主要成本来源** | 路径分叉、循环与调用展开 | 事实域大小、图规模和摘要存储 |

## 七、总结：把概念串起来

```
程序行为
   ↓ 选择要保留的信息
抽象状态与传播规则
   ├─ 数据流分析：偏序比较信息，格组织合并，不动点处理循环
   │      └─ 有限事实域 + 分配律 → IFDS：匹配路径上的事实传播
   │              └─ 加入值域与边函数 → IDE：汇总并计算值
   │                      └─ 工程优化：数据布局、批处理、回收中间结果
   └─ 符号执行：按路径维护抽象状态与约束，例如 Clang Static Analyzer
```

### 用五个问题检查是否真正理解

| 问题 | 应当能说清的要点 |
| :--- | :--- |
| 为什么污点集合取并集，初始化保证取交集？ | 一个保留任一路径的可能性，一个保留所有路径的共同保证；在本文精确度排序下，两者都是 Join |
| 为什么 IFDS 可以按单事实建边？ | 分配律允许从 `f(∅)` 和各个 `f({d})` 恢复整个集合的效果 |
| 为什么普通 BFS 不够？ | 还必须保证调用返回匹配；上下文匹配又不等于分支条件可行 |
| IDE 的边函数与跳转函数有何区别？ | 边函数描述一步值变换，跳转函数汇总过程入口到目标节点的路径效果 |
| 为什么多项式算法仍可能耗尽内存？ | 事实域可能很大，摘要条目多，数据结构和中间结果的存储成本也高 |

解释一个分析器时，先交代**事实代表什么、合并保留什么、求解精确到哪一层、成本由什么决定**，读者就能把数学定义、算法和实现联系起来。

| 符号     | 名称       | 含义                        |
| :------- | :--------- | :-------------------------- |
| `⊑`      | 偏序       | 通用的偏序关系符号          |
| `D` / `2^D` | 事实域 / 幂集 | 单个事实的集合 / 所有事实集合组成的状态空间 |
| `∈` / `∉` | 属于 / 不属于 | 一个元素是否在集合中 |
| `∪` / `∩` | 并集 / 交集 | 任一集合中的元素 / 两个集合共有的元素 |
| `⊆`      | 集合包含   | 集合之间的包含关系          |
| `⊔`      | Join       | 最小上界                    |
| `⊓`      | Meet       | 最大下界                    |
| `⊤`      | Top        | 顶元素；`(2^D, ⊆)` 中为 D    |
| `⊥`      | Bottom     | 底元素；`(2^D, ⊆)` 中为 ∅    |
| `Λ`      | Lambda     | 辅助事实，用于传播无条件生成的事实 |
| `λv.表达式` | 匿名函数 | 输入 v，返回表达式的值；与辅助事实 Λ 区分 |
| `(n, d)` | 程序点事实 | 程序点 `n` + 事实 `d`       |
